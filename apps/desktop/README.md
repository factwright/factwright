# Desktop app

The Factwright app for Mac and Windows, built with Electron and TypeScript.

It:
- runs your own installed Claude Code in a built-in terminal you can watch, without touching your login
- gives Claude the tools it needs over MCP, from saving postings to rendering resumes
- keeps your workspace and tracker on your computer, and syncs them, locked, to your other computers and your phone

## How it's put together
| Folder | What's there |
|---|---|
| [`src/main`](src/main) | The main process: the window, the app's security rules, running Claude Code ([`src/main/claude`](src/main/claude)), Claude's tools ([`src/main/tools`](src/main/tools)), your jobs ([`src/main/jobs`](src/main/jobs)), sync ([`src/main/sync`](src/main/sync)), and saving from the browser on this computer ([`src/main/extension`](src/main/extension)) |
| [`helper`](helper) | The small helper the browsers start to hand Factwright the jobs Save to Factwright saves on this computer, in C, built for the installers by `pnpm --filter @factwright/desktop helper` |
| [`src/preload`](src/preload) | The bridge: the short list of requests the window may make |
| [`src/renderer`](src/renderer) | The window's screens, built from the [design system](../../packages/ui) |
| [`src/shared`](src/shared) | The types both sides of the bridge agree on |
| [`scripts`](scripts) | The development runner, the app icons' drawing, the README's screenshots, a fix node-pty needs after every install, the helper's build, and a release's check and publishing, with a test that runs the publishing against stand-ins for R2 |
| [`build`](build) | The app icons, drawn from Factwright's mark (`pnpm --filter @factwright/desktop icon`), and what the Mac's hardened runtime allows. The installers build them in, and the app shows the icon in the Dock while you develop |
| [`release-notes`](release-notes) | What's new in each version, which installed copies show as they update |

The window is locked down:
- It runs sandboxed, with no Node and no access to files.
- It loads only the app's own files, from an `app://` address, under a strict content security policy.
- It can't navigate away or open other windows. Links to https sites open in your browser.
- The main process checks that every request comes from the app's own page.

## Installers and updates
[`electron-builder.config.mjs`](electron-builder.config.mjs) makes the installers: a Mac disk image
for Apple silicon and Intel, and a Windows installer that needs no administrator. A release signs
them, notarizes the Mac app and puts them on downloads.factwright.com
([docs/releasing.md](../../docs/releasing.md)). A copy installed from one looks there 30 seconds
after it starts and every ten minutes after, downloads a new version in the background, and shows
**Update ready** at the bottom of the sidebar ([`src/main/updates.ts`](src/main/updates.ts)). It
installs on restart, or the next time the user quits. A copy being developed, or built anywhere
else, never updates itself, unless it's built with a download site of its own, as
[Sync](#sync) says.

## Claude's panel
Claude's panel runs your own Claude Code in a real terminal (node-pty and xterm.js), in the workspace folder inside the app's data folder. Each run is locked down too:
- **No shell:** Claude Code starts in restricted mode, so it can't run commands.
- **Only Factwright's extras:** it loads only Factwright's plugin, tools and settings.
- **No outside reach:** your claude.ai connectors are off, and there's no browser automation.
- **Signals to the app:** hooks report when Claude is working, needs your answer, or is done. While a permission prompt or question is open, it keeps reading "Needs your answer", even as tools running alongside finish. A run started with nothing to do sends no hook until you type, so it reads "Ready" once Claude Code reaches Factwright's tools, which it does only past its first-run screens and the question about trust. Like a run that's done, it takes the next task you start. They go over HTTP to a server on this computer that only accepts that run's token. The token reaches Claude Code through its environment, never a file. The same server answers Claude's calls to Factwright's tools.
- **Matching colors:** Claude Code uses its ANSI theme, so the panel's colors come from the design system.

You can tuck the panel away while Claude works, and it comes back whenever Claude needs you. If you're in another app, a notification tells you.

**Claude's questions:** when Claude asks you something with Claude Code's question tool, Factwright asks it in a dialog of its own rather than the terminal ([`src/renderer/ClaudeQuestions.tsx`](src/renderer/ClaudeQuestions.tsx)), the way Claude Code's hooks allow:
- **One screen:** the whole round at once, each question with its label, its options and what they mean, a box for your own words where no option fits, several picks where Claude allows them, and a note for Claude about any answer. A question you leave unanswered is skipped.
- **Words and numbers:** a question that asks for a line of words gets a box for them, and one that asks for a number gets a box for that, with its unit. A number Claude suggests is only a hint in the box: your own number answers, as a fact can rest on it. Send waits for a number in the question's range, as Claude Code checks it.
- **Straight to Claude Code:** the question hook waits on the app ([`src/main/claude/rounds.ts`](src/main/claude/rounds.ts)), and Send answers it with your answers, so Claude Code runs its question tool with them and asks nothing in the terminal. The terminal notes your answers, as it always has.
- **Not now** puts the round aside, still waiting, with Answer in the panel to come back to it. **Answer in the terminal** has Claude Code ask it there instead, as before.
- **Waits as long as you're away:** the hook waits up to a day, then Claude Code asks in the terminal. Interrupting the run, or its ending, closes the dialog.
- **The terminal asks the rest:** a round from a subagent, one that comes with answers already, and one the dialog can't show as Claude Code would, such as a kind of question it doesn't know.
- **The same record:** Factwright's tools still file facts only from what Claude Code reports once the round has run, never from anything Claude writes. Only the app's own window can answer a round, and only one that's waiting.

**Claude Code's permission prompts:** when Claude Code asks your OK before Claude does something, Factwright asks it in a dialog too ([`src/renderer/ClaudePermission.tsx`](src/renderer/ClaudePermission.tsx)), in plain words and in full:
- **What it shows:** changing a file, with the text it takes out and puts in; writing one, saying whether it replaces a file that's there; reading a file outside your job hunt; reading a web page, with its whole address and the site it goes to; saving to your profile, field by field, including any it would clear; and saving a template, with its name, its ID, the template of yours it would replace, and its whole file to look through. A file outside your job hunt folder gets a warning.
- **No answer by accident:** its answers wait half a second after a prompt shows, so the second click of a double-click can't answer the next prompt unseen.
- **Allow or don't:** Allow lets that one call through, as Claude asked it. Don't allow tells Claude you said no, with anything you add in Tell Claude why not, and Claude carries on without it. The dialog never offers to allow anything for good: what Claude may do without asking stays as you set it in Settings.
- **Claude Code's own prompt is there too,** behind the dialog, and Claude Code takes whichever answer comes first. Answered in the terminal, the dialog closes: on a no, Claude Code drops the hook, and on a yes, the call it asked about runs, which its hooks report. **Answer in the terminal** leaves it there, and closing the dialog puts it aside, with Answer in the panel to come back to it.
- **How it works:** the PermissionRequest hook waits on the app, for up to a day ([`src/main/claude/permission-asks.ts`](src/main/claude/permission-asks.ts)), and the app answers it with Claude Code's allow or deny. A no settles the run's "Needs your answer" at once, since the call never runs.
- **The terminal asks the rest:** a subagent's request, any other tool, anything too long to show in full, such as a file of over 50,000 characters, and a path Claude Code could read another way than the dialog would, such as one that isn't whole or starts with "~".

**Pictures:** a picture pasted into the panel, such as a screenshot, is checked like any picture you share, saved in the workspace with the run's job (`screenshots/<job>/pasted-…`, or `screenshots/` without one), and pasted as where it is. Claude Code attaches a pasted picture's path as the picture itself. Screenshots added with the application's questions or a question for Claude are kept in the same folder, named for what they came with, and `job_details` lists each one.

The first run asks a question of its own: Claude Code wants to know whether to trust the workspace, and says it will be able to "execute files". When the app sees that question on screen:
- The run reads "Needs your answer", and the panel comes back.
- The terminal gets an outline that pulses a few times, then stays, until it's answered.
- A note above the terminal says how to answer: use the arrow keys to pick "Yes, I trust this folder", then press Enter.
- The note also explains that the warning doesn't apply: Claude Code has no shell here, so it can't run programs.
- The panel grows to fit the note rather than shrinking the terminal, because Claude Code can drop a line of its screen when it redraws for a resize.

Before that question, a Claude Code that's never been opened shows its first-run screens: its text style, whether to use an API key it found in the environment, its security notes, and its terminal setup. Signing in with `claude auth login` doesn't mark them done. The app marks them done itself, as [the setup check](#the-setup-check) says, so they rarely show. When they do ([`src/main/claude/screen.ts`](src/main/claude/screen.ts)):
- The run reads "Needs your answer", the panel comes back, and the terminal gets the same outline.
- A note says to press Enter on each one, that the text style only changes how Claude Code looks in your own terminal, and that the question about trust comes next and needs the arrow keys first.
- Enter clears the note, and the next screen, if there is one, brings it back.

Anything else only the terminal can answer, such as a question or permission prompt sent there, or one the dialogs leave to it, gets the same outline, with a note pointing down to the terminal: "Claude Code is asking you something in the terminal below", and how to answer. The first time, the note also says that this is your own Claude Code, until you choose Got it. The terminal takes the keyboard, so you can answer straight away.

## The setup check
Claude Code updates itself, so a new version could change something Factwright relies on. Once for each version, the app checks its setup ([`src/main/claude/self-test.ts`](src/main/claude/self-test.ts)). It starts your Claude Code hidden, with exactly what a run gets but no prompt, so it uses none of your plan. Then:
1. It waits for Claude Code to reach Factwright's tools.
2. It closes it the way you would, with Ctrl-C twice.
3. It waits for the session-end hook to arrive.

That covers the launch flags, the tools and their token, the settings, and the hooks. The result is kept in the app's data folder:
- **Passed:** nothing shows.
- **Failed:** the sidebar's Your Claude card says what went wrong, in Claude Code's own words where it can, with Check again.
- **Waiting at the trust question:** a workspace Claude Code doesn't trust yet stops at that question. The check waits for your first run, and tries again at the next launch.
- **Waiting at Claude Code's first-run screens:** the check stops at once. The Your Claude card says to press Enter through them in Claude's panel, then Check again, with Open Claude's panel while the panel isn't open.

Signing in with `claude auth login` doesn't mark those screens done, so the app does, as pressing Enter through them would ([`markFirstRunDone`](src/main/profiles.ts)). It adds `hasCompletedOnboarding: true` to the config Claude Code reads: an added profile's own, or for the first profile, `$CLAUDE_CONFIG_DIR/.claude.json`, or else `~/.claude.json`. Every other setting stays as it was. It does this when it checks Claude Code, as the window opens or comes back and on Check again, and only:
- When `claude auth status` says you're signed in with a Claude account. With an API key in the environment, those screens ask whether to use it, so they're left for you.
- While none of the app's own Claude Code is going: no run in the panel, and no setup check.
- Under Claude Code's own lock on its config, `.claude.json.lock`, so it never races a Claude Code saving its settings. It skips this time when a Claude Code holds it.

It writes the config whole or not at all, through a link if the config is one, and leaves alone a config Claude Code couldn't read either, and one in Claude Code's older place, `.config.json` in its folder, which Claude Code reads instead.

## Claude's tools
Each run gets Factwright's own tools over MCP ([`src/main/tools`](src/main/tools)), in place of a shell. The server that hears the run's hooks answers them, only for that run's token, and refuses anything a web page sends.
- **find_job:** whether you've seen a job before: its fit check, job search, folder and status. It matches the company loosely, or the posting's link alone. The skills call it before starting on a job.
- **job_details:** everything on file for a job: where it stands and, with more than one kind of job, which kind it's under, your notes, each call with its ID, who it's with, how long, how and where, what it's about, how it went and its prep sheet, the job's history, and a line for each file saved for it, saying what that file holds, so Claude knows it's there and reads what bears on the task. It also gives the application's questions with what you actually sent, your questions about the job, with which are answered, and your other jobs at the company. This is how Claude reads your tracker, without reaching its database.
- **about_you:** what you told Factwright about yourself when you started, and in Profile since, in words: your contact details, what you're looking for, each kind of job with its own titles, levels and pay, work authorization and when you can start. Skills check it before asking you anything an application asks.
- **past_answers:** what you sent on your applications, in your own words, newest first, narrowed to questions like one when asked. Claude reuses what you said, and matches how you sound.
- **save_answer:** saves Claude's answer to one of your questions about a job in `asked/<job>/<question>.md`, which the job's panel shows under the question.
- **save_call_prep** and **save_thank_you:** save Claude's prep sheet for one of a job's calls, and the thank-you notes after it, in that call's own folder, `calls/<job>/<call>/prep.md` and `thank-you.md`, which the call shows. Only a call you logged for that job takes one, and saving again replaces it.
- **save_about_you:** saves something you told Claude that applications ask for again, such as your work authorization or notice period, to your profile. Pay goes to the kind of job it's for. It changes your profile, so Claude Code asks you first, unless you let Claude change any file, or the run is for getting to know you.
- **read_posting:** a posting on Greenhouse, Lever, Ashby or Gem, read from the applicant system's public feed and never the page the link names.
- **read_page:** any public web page as plain text, such as a posting on another site, a careers page or a team page. It answers with at most 40,000 characters, since Claude Code moves longer answers somewhere Claude can't read.
- **save_posting:** saves a posting word for word in the job's folder: what read_posting or read_page read from that link in the run, or a posting read from its applicant system's feed. It reaches no other site. A posting already saved there is kept.
- **build_resume:** builds a job's resume from its `resume.json`, or a starting resume from `base/<name>.json` (or `base/<kind>/<name>.json` for a kind of job after the first), with the [resume engine](../../packages/engine), as a PDF, a Word file or both. It checks the resume against your rules and confidential terms, and says how many pages it runs to, how full the last one is, and which lines run short. Once you've applied to a job, it keeps the files you sent.
- **build_cover_letter:** builds a job's cover letter from its `cover-letter.json`, as a PDF, a Word file or both, in the template of the job's resume unless the letter names its own, with the same header, so the two look like a set. A template without a letter layout prints it plainly, in its fonts and colors. It checks the letter against your rules and confidential terms, the clichés every cover letter is checked for, and the resume's header, and says whether it fits one page and which paragraphs end on a word or two. Once you've applied to a job, it keeps the files you sent.
- **list_templates**, **read_template** and **save_template:** the resume templates the user can pick, built in and their own; a template's file, to start another from; and saving one Claude made, once it passes the engine's checks, with a printed preview for Claude to read, of a resume and a cover letter. Saving asks first, unless the run was started to make a template. It replaces one of the user's templates only when asked to. A run started to make a template can replace only the ones it saved itself, and any other run's replacement puts the one before in the trash.
- **job_board:** every open job on a company's board on Greenhouse, Lever, Ashby or Gem, saved word for word as one file in a job search's folder, with a list for Claude: where each job is, its pay, when it was posted, and its link. Given a link to one posting, it says whether that posting is still open. Only the board's name goes to the applicant system's API.
- **hn_jobs:** every job post in Hacker News's monthly "Who is hiring?" thread, saved word for word as `hn-thread.md` in a job search's folder, with each post's first line for Claude. A long thread comes with where each run of 50 posts sits in the file, so Claude can split the reading between helpers.

Reading and saving only fetch public https sites, never this computer or your home network, and give up on pages that are too big or too slow. A whole board can run to 25 MB, since big companies' boards carry every posting in full; a page stops at 5 MB.

The tools that stay on this computer run without asking, apart from save_about_you, as do web searches and Factwright's skills. So do read_posting, save_posting, job_board and hn_jobs: they reach only the applicant systems' and Hacker News's public feeds, and send them nothing but a board's name, a posting's ID or a month. Claude also saves its work in `applications/`, `searches/` and `outreach/` without asking, and adds to `guide/confidential-terms.txt`, which only makes the resume check stricter.

Each task runs on a model recommended for your plan, which `claude auth status` reports when the run starts. On Max, Team and Enterprise it's Opus. On Pro, whose limits are tightest, and with an API key, a Console account or a cloud provider, where every token is billed, fit checks, salary checks, job searches and who to message run on Sonnet, and the rest on Opus. `claude auth status` doesn't say which Max tier or kind of Team seat someone has, so those all get Opus. **Your Claude → Settings** picks the model for everything, and for each task the app starts (each Run button, and Find jobs). The app passes it with `--model`. A model you never picked follows your plan when it changes, and one you picked stays yours. When Claude is open on another model than a task needs, the app starts a new run on that model instead of switching the open one, since `/model` would also change your own Claude Code default. That includes a lighter one, such as Sonnet for a job search on Pro, as that's what saves the most of a plan.

Each task also has an effort: how long Claude thinks before it acts. Restricted mode ignores your own Claude Code settings, so the app sets it with `--effort`, by your plan, the same way. On Max, Team and Enterprise it's extra high, except job searches at high, since they read hundreds of postings and weigh each one lightly. On Pro, and wherever every token is billed, it's high, and medium for salary checks and job searches. Max is yours to pick, since it can take many minutes a run. The same settings change it for everything or for one task. A task that needs more effort than the open run starts a new run the same way, since `/effort` would change your own default too; one that needs less runs in the open run, at its effort, so a salary check after a fit check doesn't start Claude over. Claude Code lowers a level a model can't reach on its own.

Under **Your Claude**, the sidebar shows the levels most tasks run at, such as "Opus · Extra high", and a few words on any that differ. Its tooltip says what's best overall, what's best on your plan when that's lower, and that results can vary with the level. Clicking it opens the same settings.

Claude Code asks you before each page read_page fetches, since it reaches any site: a job post could otherwise steer Claude into sending your details to a site in a link. It also asks before Claude changes any other file, such as your facts. **Your Claude → Settings** lets you turn either question off, from Claude's next start; the choice is kept in the app's data folder, outside the workspace, so Claude can't change it. Whatever you choose, Claude never changes Claude Code's settings or the instructions Claude Code loads (`.claude/` and `CLAUDE.md`).

## Printing resumes
The main process prints resumes in one hidden window ([`src/main/resume`](src/main/resume)), with Chromium's own layout, so the PDF matches what was measured:
- **Locked down:** the window has its own session, kept in memory. It loads only the page it's given, and every other request is refused, so a resume can't reach the network or your files.
- **The last page:** after printing, it finds how full the last page is by printing again with a growing spacer at the end, until the spacer would start a new page.
- **Fonts:** every resume carries the [engine's fonts](../../packages/engine/fonts), built into the app, which stand in for the Windows fonts the layouts were designed with. So a resume prints the same on a Mac as on Windows, down to where each line breaks. The window loads each one before it prints or measures.

## Getting started and Profile
A new user, with no jobs and no fact bank yet, opens on **Get started**: seven short steps, saved as they go (in the workspace's `about-me/` folder), so they can stop and pick up later.
- **Welcome:** what Factwright does, that it runs their own Claude Code and never sees its login, and their Claude's state. When Claude Code is missing, signed out or too old, the steps to fix it, with the exact command to copy and a button that opens Terminal (PowerShell on Windows). The user runs it themselves; the app checks again when they come back. Where a new terminal window wouldn't find Claude Code by its name, the commands start it by its whole path ([`src/shared/claude-commands.ts`](src/shared/claude-commands.ts)), with a link to Anthropic's guide to adding it to PATH: Claude Code's installer never adds its folder on Windows, and may not on a Mac. A new PowerShell window has the PATH the app has, and on a Mac the app asks the login shell, which has the PATH a new Terminal window has. Someone who already uses Factwright on another computer can turn on sync instead, in a copy built with a sync server.
- **About you:** their name and contact details, as resumes should show them.
- **Your files:** resumes (PDF, Word or text), their LinkedIn profile saved as a PDF, LinkedIn's own export of their data as a ZIP, and screenshots and other documents. The window reads the text out of PDFs (with pdf.js) and Word files, and out of the LinkedIn export it keeps only the profile's spreadsheets and the connections. The app checks each file again before keeping it ([`src/main/about`](src/main/about)).
- **In your words:** a big box for everything about them, with prompts to start from, and the names to keep off every resume.
- **What you want:** job titles, kinds of work, levels, where, kinds of company, industries, pay, terms, must-haves and deal-breakers, and a quiet search. Someone after more than one kind of job, such as developer and project manager jobs, adds another kind: each has its own titles, kinds of work, levels and pay, and its own starting resumes, and the rest holds for all of them. They're kept in `about-me/kinds-of-job.json`, apart from `answers.json`, which keeps the first kind's, so a copy of the app from before kinds never drops them. Nothing about kinds shows until there's a second.
- **Templates:** the resume templates, the app's two and any of their own, each a real print of a sample resume with their own name on it, and the ones that suit them picked for each kind of company they're aiming at. They can bring a resume whose look they like, as a PDF or a picture, for their Claude to make a template from, or a template file someone shared. Plus the length and the files.
- **Ready:** a summary, what happens next, and Start with your Claude, which copies in the starter files the workspace lacks, writes the files built from the answers, and starts `/factwright:get-started`.

**Profile** follows Claude as it drafts the fact bank, confirms it with the user and builds their starting resumes, then keeps every answer changeable: the fact bank (with how many facts are left to confirm, and anything shared since Claude last read), the starting resumes (to preview, open, or build again, by kind of job when there's more than one), what they want, their templates, what they've shared and their contact details. The files built from the answers (`searches/criteria.md`, `guide/templates.md` and the page count in `guide/lint.json`) follow each change, unless someone has changed them by hand since.

**Fact bank** ([`src/renderer/facts`](src/renderer/facts)) shows `facts/` file by file:
- **Each claim** is a card: its tags in words (Live, Led and built, High confidence), the words resumes use, and its details. Each file's other sections, such as its overview, show around them.
- **Search** reaches every file, and **To confirm** gathers the facts drafted from your files that you haven't checked.
- **Changing a fact** happens in a form, so its tags stay ones the skills know. A section changes as Markdown. Confirming a fact does what the skills do: it drops `unconfirmed` and makes you its source, with the date.
- **Each change** goes to the main process as one block, the way the window read it ([`src/main/about/facts.ts`](src/main/about/facts.ts)). A block that changed since, such as by Claude or another computer, is refused rather than overwritten, and the rest of the file stays byte for byte. Only Markdown files already in `facts/` change, each saved whole or not at all, never through a link.

A run started for getting started or for more facts may save the facts, starting resumes and guide without asking each time, which every other run asks before doing, and it can't reach the web at all. A run started to make a template may read and save templates without asking, and nothing else: it can't reach the web either, and asks before building a resume, saving an answer or changing any file, since the resume it copies came from anywhere. Each tool call knows which run it's from, so that run can replace only the templates it saved. The app keeps that resume in `templates/sources/`, under a name of its own, and names it to Claude by that. A task that needs other permissions, or another model, starts a run of its own.

## Your jobs
Your jobs come from two places, joined into one list:
- **The workspace:** what the skills save there, such as fit checks, job searches, and each job's folder with its posting and resumes. The app reads it with [`@factwright/core`](../../packages/core), and reads it again whenever something changes, so new work shows up on its own.
- **The tracker:** what you set by hand, such as statuses with their dates, applied dates, next steps, dated notes, calls with who they're with and how they went, and an application's questions. It's a small SQLite database (Node's built-in `node:sqlite`) in the app's data folder, beside the workspace rather than in it, so Claude's file tools can't reach it.

Each job keeps its ID in the tracker, so your notes stay with it as new work comes in. A job you've tracked stays listed even if its files go away.

The jobs screen ([`src/renderer/jobs`](src/renderer/jobs)) follows the approved mockup:
- **The list:** the numbers that matter (in play, applied, heard back, needs you), the views in the order a job moves through them (new, to review, to apply, applied, interviewing, closed, and all), search across companies, roles and notes, and each job's next step. Jobs in interviews show their calls so far, and new jobs say which search found them. Rows reflow to fit the window instead of scrolling sideways. It opens on the view you last picked, or the first time, the one furthest along with jobs in it.
  - **Kinds of job:** with more than one, **Kind of job** in the toolbar shows one kind's jobs, and the numbers above follow it. While every kind shows, each job says which it's under. A job is under the kind you put it under in its panel or in Add job, or else the one the job search or fit check found it as, or else your first until a fit check says, as its panel shows. Add job can leave it to the job's fit check.
  - **Statuses** say what you decided. New is a job nobody has touched. Claude's work on it (a fit check, a salary check, a question, a resume) moves it to To review, and only you move it further: To apply, Later, or Passed, then Applied onward. A job set aside for Later folds at the bottom of To review, outside its count, and comes back up on the day you give it, marked "Back from Later". Role closed is for a posting that came down or a role that was cancelled, before or after you applied.
  - **Select several jobs** with the boxes beside them, or Shift for a run of them, to move or pass them all at once. A bar under the list moves them, then asks why you passed, or when jobs set aside come back, with Undo.
- **Find jobs:** asks where to look: Hacker News's "Who is hiring?" thread (the newest, or a month), LinkedIn, Indeed, companies' job boards on Greenhouse, Lever, Ashby and Gem, or a company you name. Claude finds LinkedIn's and Indeed's listings through web search and reads each job on the employer's own site; Factwright's tools never read LinkedIn's pages. Then it starts the search in Claude's panel, the same safe way as the Run buttons: the app types `/factwright:job-search` and the places itself (`HN · LinkedIn`), and a company you typed only once it checks as a name or an https link. Each place is a search of its own, and **Found by** narrows the list to one, such as the month's HN thread. The jobs that fit land under New.
- **The job panel:** everything on file for the picked job, under a header that stays in view, with its status, which you can change from a menu grouped into before applying, after applying and closed. **Expand** gives the job the whole window, in two columns, with the previous and next jobs in the list a click away; Escape puts it back. A new job, or one to review, leads with a fit check and its quick choices: To review, To apply, Later and Pass. A job set aside asks when it comes back, and one passed on asks why, in a click, for the job searches to read. Accepting an offer offers to withdraw from the other jobs still in play, in one step. The next step, with a date that puts it in "Needs you" when it's due, and how to apply, when there are special steps, come first. The rest is in sections that open and close, and stay as you left them:
  - **Progress:** each step the job has taken, from found to where it is now, with its date, and the step ahead. The dates of the steps you marked, and the applied date, can be fixed in place, and Undo takes back the latest change.
  - **Calls and interviews:** each step of the company's process, in the order they happen. Add a call with its kind, when, how long, by phone, video or in person with its link, number or address, who it's with and their roles, and what it's about; adding one moves the job forward, and the form starts on the round after the last. Every detail can be changed later, a call can be canceled, and deleting one asks first. The next call booked is marked Next, and an https meeting link opens with Join.
    - **Before it:** Call prep has Claude write a prep sheet for that call (`/factwright:interview-prep job <id> call <call id>`), which the call keeps, beside Prep again, and Practice runs a mock interview for it. The window sends only the job's and the call's IDs, as with every Run button.
    - **Once its time comes:** How did it go, and a box for how it went, in your words, which the next round's prep reads. Thank-you notes has Claude draft one for each person you met, each with its subject and words to copy, and Add the next round follows a call that moved forward. A call today with no time given shows both all day.
    - **In your calendar:** Add to calendar, on a call still to come, saves a calendar file (`.ics`) where you pick, through the system's own save dialog, named for the call, the company and the day in plain characters. It gives the call's title, its day and time as you gave them, as a floating time with no time zone, as the app keeps it, its length (an hour if you didn't say), the meeting's https link or else the address or number, and in its notes the role, who it's with, how it happens and what it's about. A call with no time is an all-day event. It's published as an event with no attendees, so opening it invites no one.
    - **From an invite:** drop an invite's `.ics` file on the Add a call form, or pick it with Fill in from an invite, to fill in the date, time and length, where it is, and who it's with, by the names it gives. An address or a number to call is the place even beside a meeting link, as Google adds a Meet link to every event, an onsite one too; otherwise the place is the video call's link, which also makes the call Video. A link counts as a meeting's only when it's on a video call site, the invite names it as its conference, or the location is that link alone, so a scheduling page or a map doesn't. The time moves into the computer's time zone, whether the invite gives it in UTC, a named zone or the rules Outlook sends for its own zones; when the zone can't be read, the time is as written and the form says to check it. You, by your profile's name and email, rooms, and anyone who declined or isn't taking part are left out, and people met already at the company bring their roles. The file is read in the window, with no Claude and no network, as untrusted text: only these plain fields, each cut to the form's limits, without characters that hide or flip text, and no link but a video call's https one. Nothing is saved until you add the call.
    - **A reminder:** an hour before a booked call that has a time, on a job that isn't archived, a notification says "Panel interview with Northwind Labs at 2:00 PM", and whether its prep sheet is ready. Clicking it brings Factwright forward, or opens its window again on a Mac, on that job. It comes while Factwright is open, even with no window on a Mac, once per call, which the app keeps in `call-reminders.json` in the profile's folder: a call moved to another time gets one for its new time, one added or moved in its last hour gets none, even after a restart, and one whose hour began while the computer slept, or before Factwright started, gets it straight away, until the call starts. So does one that comes by sync, made on another device before. The next call says a reminder is coming, with Turn off, which turns reminders off on this computer until you turn them on again there.
  - **Notes:** jot down what was said on a call, names, anything to remember. Each note is dated today, or the day you pick, newest first, and you can change or delete it. Notes from before notes had dates stay at the end.
  - **Your Claude:** what Claude can do for the job.
    - **Run with your Claude:** a tailored resume, a cover letter, a fit check, a salary check, who to message, interview prep, or the application's questions, started on this job in Claude's panel. Each says where it stands (Run, Running, Done, or Ran and Ready for work already on file), and the next step for the job is highlighted. The window sends the app only the skill's name and the job's ID, and the app types the command (`/factwright:fit-check job <id>`), so text from a posting never reaches Claude as if you'd typed it. Claude that's open and done takes the next one; otherwise Claude starts with it.
    - **Application questions** asks for the form's questions first, one box each, or screenshots of the form, and keeps them with the job however the dialog closes. Answer with Claude starts the run, and Claude reads the questions through `job_details` as questions to answer, never as commands.
    - **Ask Claude:** your own questions about the job, such as what to expect from a call, each with Claude's answer once it's in, kept to come back to. A question can come with screenshots, such as an email from the recruiter. Asking keeps the question in your tracker and starts `/factwright:ask job <id>`, and Claude reads the question through `job_details`, the same way as the application's questions.
  - **Fit:** why it scored what it did, part by part, with the evidence, what people say about the company, and what the job search noted
  - **Cover letter,** once Claude has written one: the letter, Copy text for an application form's cover letter box (the greeting, the letter and the closing, as plain text), and its PDF and Word files to preview or open. When a posting asks for a cover letter, it's the job's next step once you've decided to apply, and its Run button is highlighted once the tailored resume is ready, since the letter copies its header. While Claude writes the letter, the section says it isn't checked yet.
  - **Application answers:** each of the application's questions with Claude's suggestion, and a box for what you actually sent, which saves as you type. It's there to look back on when the job moves on, and Claude reads it before your interviews.
  - **Files:** its resumes, cover letters and documents. Preview shows a resume PDF's pages right there, exactly as an employer will see them, drawn by [pdf.js](https://github.com/mozilla/pdf.js). pdf.js loads only when a preview opens, and draws pages the way it prints, so a preview finishes even with the window in the background. The window can read only PDFs in your workspace, up to 20 MB.
  - **History:** everything that happened with the company, newest first: each call with who was on it and how it went, your notes, each change of status and Claude's work, across your jobs there, with the people you've met at the top
  - archiving, which takes it out of your lists without losing anything

  Beside the list when there's room, and over it when the window is narrow.
- **Adding a job:** the top bar's Add job button, for jobs you found yourself. It links to Save to Factwright, the browser extension, for a job found in the browser, which can save straight to Factwright on this computer ([below](#save-to-factwright-on-this-computer)).
- **Filters:** fit, minimum pay, has a resume, and archived jobs.
- **Your journey:** how far your jobs got and how they ended, as a summary or a flow chart of every path they took, drawn in the app. It also copies the paths as text for sankeymatic.com, or saves a spreadsheet with each step's date. With more than one kind of job, it shows one kind's, or compares them side by side, and the spreadsheet says each job's kind.
- **Opening files:** documents open formatted, in the app. Resumes open in your own PDF or Word app, and only PDF and Word files inside the workspace can open that way.
- **Copying and saving:** the window asks the main process. Saving a file always goes through the system's save dialog, so you pick where it goes.

## Sync
Sync keeps your workspace and tracker the same on each of your computers, and your phone, locked before they leave ([`src/main/sync`](src/main/sync)). It's off until you turn it on, from the sidebar's Sync card. The design is in [docs/security.md](../../docs/security.md).
- **Choosing a server:** turning sync on offers Factwright's sync and a server of your own side by side. Factwright's shows its price, and "Money's tight?", only once its server lists a `subscription` feature in `/api/sign-in-options`, as it does while it sells sync, and the terms line shows only for a server that names its terms ([`src/renderer/sync`](src/renderer/sync)).
- **A server of your own:** Connect your server… takes its address, such as `https://factwright-sync.yourname.workers.dev`: https, with nothing after it and no user name or password, or http for one on this computer, for testing. The app checks it answers `/api/sign-in-options` as a Factwright sync server with what this version needs, and says to use only a server you run or trust. The sign-in is kept with the server's address, locked with it in the keychain, so its token only goes there, and the Sync screen names it. To use another, turn sync off on this computer first ([`src/main/sync/server.ts`](src/main/sync/server.ts), [docs/security.md](../../docs/security.md#a-sync-server-of-your-own)).
- **Signing in:** your browser opens the server's sign-in page, where you sign in with GitHub or Google, check it shows the code the app shows, and allow it. To a server of your own there's no code: you allow it, and the browser comes back to the app at its address on this computer, 127.0.0.1 (`src/main/sync/loopback.ts`), with an answer the app takes only from the server it asked. The app gets its own session, and opens only the sync server's own pages.
- **Subscribing,** where the server sells sync and the account doesn't have it: after signing in, before the recovery key or linking, Subscribe in your browser opens the server's `/subscribe` page, naming the account by its ID, so the page can say if the browser's signed in as someone else. Paying happens there, never in the app. The app asks the account every few seconds, then every ten, for as long as checkout stays open, and carries on by itself once it has sync. Opening the step asks once too, for someone who subscribed from their phone. An account with a subscription, free sync or from before sync was sold skips the step. It offers a server of your own instead, and "Money's tight?".
- **The first computer** makes the account key, and shows your recovery key once, to copy or save as a file before sync turns on.
- **Every other computer** links with a code from one that's set up, or with the recovery key. Link a phone or computer shows the code, with a QR code for a phone's camera.
- **Secrets:** the session token and the account key are locked with the system's keychain (Electron's safe storage) before they're written to the data folder. The keychain isn't touched until you turn sync on. An installed copy started with a debugging port, as its tests are, never asks it for sync's keys, as on a Mac every copy of the app shares one Keychain item: sync can't turn on there.
- **What syncs:** every file in the workspace, and every row of the tracker: jobs, their history, calls and notes. Hidden files, other apps' temporary files, files over 25 MB and names Windows can't hold stay put, and the dialog says how many.
- **When:** a moment after each change here, right away when another device changes something (the server tells each listening device), and every ten minutes anyway. Offline, it waits and tries again, and your changes stay safe here.
- **When both changed something,** nothing is lost. A file keeps both: the other device's version in its place, and this computer's beside it, named with the computer and the day, like `notes (Sam’s Mac, Oct 12).md`. A tracked job merges: its links, questions, the answers you sent, your questions for Claude, and its notes keep both sides, and the later change wins a clash. A note changed elsewhere shows up in the job panel unless you're typing in it.
- **Paused:** once a subscription ends, the server turns down sending (402), and sync stops here, as it does when signed out, rather than trying again after each change. The Sync card says Paused, and that the job hunt here is safe: that the subscription ended, or, for an account that never had one, as when free sync ended, that sync needs one now. The sign-in and the account key stay, and so does Paused after a restart. A paused computer asks the account whether it has sync again as it opens, on coming back to the app or the computer waking, and every half hour, so it carries on by itself after subscribing from another device. Subscribe again… opens the page for it, and sync picks up where it left off, sending what changed meanwhile. An answer about the account from before sync paused or carried on is passed over, and a request that doesn't get through as it carries on leaves it paused, to ask again.
- **A card that didn't go through:** while Stripe tries a renewal's payment again, sync carries on, and the Sync card says "Card didn't go through", with Update card…. It opens the Sync screen, which says so at the top, with Update card, which opens your account on the web. The app asks how the account has sync after its first round of sync, once an hour after that, and whenever the Sync screen opens.
- **Managing it:** the Sync dialog lists your signed-in devices, signs any of them out, makes link codes, turns sync off on this computer (its job hunt stays), and opens your account on the web, to download everything or delete the account. Where sync is sold, it says when the subscription renews or ends, that a card didn't go through, or that sync is free and why, with Manage, which opens the account page, where Stripe's portal manages it. It links to Save to Factwright, the browser extension, which saves jobs through it, with Factwright's sync or a server of your own.
- **Only Factwright's own builds,** made by its release workflow, have its sync server, app.factwright.com, and its download site. A copy built anywhere else, such as from a fork or on your own computer, has neither: it syncs only through a server of your own, and it never looks for updates.
  - **To sync a copy you build,** run a [sync server](../server#running-your-own) of your own, and connect it in the Sync dialog, as any copy can. To build one in as the copy's own, set `FACTWRIGHT_SYNC_SERVER` to its address for `pnpm --filter @factwright/desktop build`.
  - **For updates,** set `FACTWRIGHT_DOWNLOADS_URL` to a site of your own for `dist:mac` or `dist:win`, which write it into the installers, and put each version's installers and its `latest.yml` or `latest-mac.yml` there, as [docs/releasing.md](../../docs/releasing.md) describes. A Mac copy installs an update only if the two are signed with the same certificate, so a copy built without one never updates; to give copies to other people, that's a Developer ID certificate.

## Save to Factwright on this computer
Save to Factwright, the browser extension ([`apps/extension`](../extension)), can save straight to Factwright on the same computer, with no account and no sync. The browser hands each job to a small helper the app carries ([`helper`](helper)), through its native messaging, and the helper drops it in an inbox in the data folder of the profile open last ([`src/main/extension`](src/main/extension)):
- **Registering the helper:** the app tells each browser where the helper is, and that only Save to Factwright may start it: Chrome, Chromium, Edge, Brave, Arc, Vivaldi and Firefox, each in its own place for native messaging hosts.
  - **On Windows,** that's a key under `HKEY_CURRENT_USER\Software` naming a file in the app's data folder, for each browser it finds, as the app starts, and again after each update.
  - **On a Mac,** it's a small file in each browser's folder in `~/Library/Application Support`, which macOS keeps from other apps: reaching one, the app gets blocked, and macOS says so, until the user allows it. So the app never touches a browser's folder until the user sets that browser up in the Save to Factwright window (Browser extension, in the sidebar), which says first that macOS may ask the user to allow it, once for each browser, or block it. It finds the browsers by their apps in Applications, never their folders. A browser macOS refused shows as such, with the steps to allow it in System Settings, under Privacy & Security, then Files & Folders, and a button that opens it. Once a browser is set up, a start writes its file again only if the app has moved or the file would read differently.
  - **The record:** the app notes what it did in `save-helper.json` in its data folder: the browsers set up, and on a Mac the ones macOS refused. A copy run from its disk image, or that macOS hasn't moved to where it lives yet, registers nothing, as that place goes away, and nor does a copy another program drives, as the tests do. Uninstalling on Windows takes the registrations away.
- **The helper** reads one message, takes it only if it's a job and nothing else (its link, site, title, company, pay and posting), and writes it whole into `inbox/` in the profile's folder, beside the workspace, so it never syncs and Claude's tools can't reach it. With the app open, it waits up to three seconds for the app's answer, and hands it back to the extension, or else says the app adds it in a moment. With it closed, it says the job waits.
- **The inbox:** while the app is open, it adds each job as it comes, and the ones that came while it was closed as it starts: as New, with its posting kept in `saved/<job ID>/posting.md`, as a save through sync does, so sync carries it to your other devices if it's on. The same job, by its link, is added once. Anything that isn't a job is deleted, with nothing in it kept.
- **Trying it from the code:** `pnpm --filter @factwright/desktop helper` builds the helper. A copy run from the code registers it only when `FACTWRIGHT_EXTENSION_ID` names an unpacked extension to allow, beside the stores' build, as `chrome://extensions` shows its ID. On a Mac, set the browser up in the Save to Factwright window, as an installed copy does.

## Profiles
People who share a computer each keep their own job hunt in a profile of their own ([`src/main/profiles.ts`](src/main/profiles.ts)). A profile is also a fresh start, for trying a setup from scratch.
- **What's in one:** a whole data folder: the workspace and tracker, sync's session and keys, Claude's settings, and the window's own storage. Each signs in to its own sync account and its own Claude.
- **Where:** the first profile is the app's data folder, as it was before there were profiles, so a job hunt from an earlier version stays where it was. Each profile added gets a folder under `Profiles`, inside it, named by a random ID, so a new profile won't land in a removed one's folder. `profiles.json` beside them says which profile opens.
- **Adding one:** from the bottom of Profile, or Get started's first step. The first time, it names the profile that's open too.
- **Switching:** one profile is open at a time. Switching, from the top of the sidebar once there are two, notes the choice and restarts the app. As it starts, the app opens that profile's folder before anything else uses it, so Chromium's storage, and the lock that keeps one copy of the app on a folder, go with it. An update that's ready installs as the app restarts. Switching waits while Claude's run is open. If a profile's last start stopped short of its window, the next start opens the first profile instead, and says so.
- **Claude:** the first profile uses your own Claude Code setup. An added profile runs Claude Code with `CLAUDE_CONFIG_DIR` set to its own `claude` folder, so its login, plan, settings and history are its own, and leaves any Claude login in the environment out. Get started and the Claude card show the command that signs it in.
- **Sync:** each profile signs in to its own account. Signing in to one that another profile here uses is turned away.
- **Removing one:** Manage profiles moves an added profile's folder to the trash, never the open one or the first, whose folder holds the others.
- **Not private:** anyone who can use the computer login can open any profile. Separate computer logins keep job hunts private, as [docs/security.md](../../docs/security.md#profiles) says.

## Run it
- **The app:** `pnpm dev` from the repo root opens it. The screens reload as you edit them, and the app restarts when the main process changes. Extra arguments go to Electron, such as `--remote-debugging-port=9223`. Switching profiles closes it, since the screens' server closes with the app: run `pnpm dev` again to open the profile chosen.
- **The screens alone:** `pnpm --filter @factwright/desktop screens` shows them in a browser with sample data, for checking the design.
  - `?claude=signed-out` picks Claude's state (also `missing`, `too-old`, `unknown` and `checking`). With `?path=off`, a new terminal doesn't find Claude Code by its name, so the steps start it by its whole path, as they do while it's missing.
  - `?jobs=none` shows the screen before there are jobs (also `failed` and `loading`). Otherwise made-up jobs show every state. Edits, such as logging a call or adding a job, stick until a reload.
  - `?platform=win32` shows the Windows title bar layout.
  - `?sync=on` picks sync's state (also `off`, `first`, `link`, `signing-in`, `syncing`, `offline`, `problem`, `signed-out`, `unavailable` and `no-server`). Turning it on plays through each step.
  - `?profile=done` shows a finished profile (also `new` and `started`).
  - `?profiles=two` shows two profiles, with the switcher at the top of the sidebar (also `added`, with an added profile open, whose Claude signs in with a command of its own).
  - Start Claude plays a short made-up run, including a question. With `?run=asks`, interview prep stops to ask one too.
  - `?open=<job ID>` opens a job, as clicking a call's reminder does, and `?reminders=off` starts with reminders before calls turned off.
- **The README's screenshots:** `pnpm --filter @factwright/desktop screenshots` takes them again from the same sample data, each framed as a Mac window, in light and dark, into [`docs/images`](../../docs/images). Take them on a Mac, after a change they show. It needs Playwright's Chromium, once: `pnpm --filter @factwright/desktop exec playwright install chromium`.
- **The built app:** `pnpm --filter @factwright/desktop build`, then `start`.
- **Sync against a server on this computer:** set `FACTWRIGHT_SERVER_URL`, such as `http://localhost:8787` for the [sync server](../server) run with `pnpm --filter @factwright/server dev`, and it's Factwright's sync. Without it, a copy you run from the code has no Factwright's sync, unless it was built with `FACTWRIGHT_SYNC_SERVER`, and connects `http://localhost:8787` as a server of your own instead.
- **End-to-end tests:** after a build, `e2e` drives the built app with [Playwright](https://playwright.dev) through its main flows ([`e2e`](e2e)):
  - It runs on a made-up job hunt in a fresh data folder.
  - A stand-in for Claude Code ([`e2e/fake-claude`](e2e/fake-claude)) comes first on PATH. It answers the version and sign-in checks, and in a run reaches Factwright's tools and sends its hooks as Claude Code does. It never reaches Anthropic, so the tests use no plan.
  - One test leaves it off PATH instead, where an installer puts it in a home folder of the test's own, with only the system's folders on PATH, and checks that the steps start it by its whole path. A unit test runs those commands in zsh, bash, sh and PowerShell, whichever the computer has, against a stand-in where Claude Code's installer puts it.
  - `FACTWRIGHT_QUIET=on` keeps the app out of the way of whoever is using the computer meanwhile: its window never takes the keyboard, it has no Dock icon, and notifications are only asked for, with the app's `quiet-notification` event. On a Mac the window stays hidden. On Windows and Linux it shows without being brought forward, as Chromium there stops drawing a window that hasn't shown. The tests always set it. Set it for any other launch of the app while someone works on the computer, too. An installed copy ignores it.
  - `FACTWRIGHT_SETUP_WAIT_MS` shortens the setup check's wait, so the tests see it finish.
  - `FACTWRIGHT_RELAUNCH=off` makes switching profiles close the app without starting it again, so the test opens it again itself. An installed copy ignores it. The stand-in reads as signed out in an added profile's own Claude Code folder, until the test signs it in.
  - Sync's tests run two copies of the app against the [sync server](../server), run locally in workerd, with a stand-in keychain: one turns sync on, the other links with a code, and a change on one shows up on the other.
  - CI runs the tests on every change, on Linux, with a virtual display.
  - A [Windows workflow](../../.github/workflows/windows.yml) runs the unit and end-to-end tests on Windows: weekly, by hand, and when its file changes. It doesn't run on every change, because Windows minutes cost twice as much on GitHub's free plan. Its stand-in is `claude.cmd`.
