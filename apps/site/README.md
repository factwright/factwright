# Website

factwright.com: one page that explains Factwright and shows how it works, its download pages, a page for its browser extension, a page about sync and what it costs, a guide to running your own sync server, its roadmap with ideas to vote on and suggest, its privacy policy and terms, and a "not found" page. It's static, but for the roadmap's ideas, which its Worker fills in: the pages read fine without their script, which adds the motion, the guide's tools, and the roadmap's votes and suggestions.

It's built on the design system in [`@factwright/ui`](../../packages/ui): its colors and fonts come from the same tokens as the app, in light and dark, so the drawings of the app's screens match the app itself.

## Running it
```bash
pnpm --filter @factwright/site dev
```

It opens at http://localhost:5173 and reloads as you change it. The download pages show the version only through the Worker, once a release is out, and without it their download links do nothing. The roadmap's ideas show only through the Worker too. To see it the way Cloudflare serves it, with the Worker and its headers, run `pnpm --filter @factwright/site serve`: it builds the site and serves it at http://localhost:8788. `--local-upstream` keeps the local address; without it, Wrangler hands the Worker factwright.com, which it sends to https.

The roadmap needs its database, which Wrangler keeps on your computer for `serve`. Make its tables once, and again after a change to `migrations`:

```bash
pnpm --filter @factwright/site exec wrangler d1 migrations apply factwright-feedback --local
```

Suggest a few ideas on http://localhost:8788/roadmap, then approve them on its admin page. No Cloudflare Access stands in front of a local preview, so the admin page lets no one in unless `apps/site/.dev.vars`, which git leaves out, names who's signed in there: `LOCAL_ADMIN=you@example.com`. It works only on localhost.

After changing a resume template, a link preview card or the extension page's drawing, draw the pictures again, on a Mac so the cards get the system font. It needs Playwright's Chromium, once: `pnpm --filter @factwright/site exec playwright install chromium`.

```bash
pnpm --filter @factwright/site images
```

## Security
The pages run only the site's own scripts and styles, connect to nothing but the site itself (the Worker reads the update feeds, not the page), can't be shown inside another site, and keep to https. The roadmap's script is the only one that connects at all, to the site's own API, and no form sends itself anywhere: the roadmap's forms are sent by its script. So the own-server guide's tools work in the page alone: the subdomain someone types and the secret it makes never leave it, and nothing is kept. The site has its own address, apart from the web view at app.factwright.com, so nothing on it shares the address where the web view keeps its keys.

## Search
Every page has a title. Every page but the "not found" page, which asks search engines to skip it, also has a description and a canonical address, and the home page and the extension's page have the cards that link previews show. `public/robots.txt` lets search engines in, and `public/sitemap.xml` lists the pages worth finding.

The home page also tells search engines what Factwright is, in a block of JSON-LD in its `<head>`: free, for macOS and Windows, from Neatifai LLC. It's data, not a script, so the security policy above doesn't apply to it and stays as it is.

The drawings of the app show made-up jobs, so each one carries `data-nosnippet`, which asks Google and Bing to leave those companies out of the snippets they show. When you redraw one, keep it, and add any new made-up company or person to `MADE_UP` in `test/pages.test.ts`. The tests check that each drawing carries it, and that no made-up name sits outside a marked part of the page, not even in the title or a description.

## Ideas and the roadmap
Anyone can suggest a feature on `/roadmap` and vote for the ideas there, with no account. Report a problem stays an email to steve@factwright.com, from the app's sidebar, and GitHub's issues stay for developers. The board lives in the site's Worker, with its own D1 database, `factwright-feedback`, not in the sync server, whose code is what people deploy as their own servers.

- **Suggestions** come in as `new`, which only the admin page shows. Each has a title, a few lines, and an email to hear back, if its suggester gives one, kept only to write to them by hand and never shown. While 200 wait, more are turned away, so a flood can't fill the database. Emails to Steve about new ones wait for a way that keeps his address out of this public `wrangler.jsonc`, which Email Routing's `send_email` binding would put there.
- **Votes need no account.** A browser's first vote, or suggestion, makes a random voter ID, kept in its `localStorage` for the site, never a cookie, with the ideas it voted for. A vote sends only SHA-256 of `voterID:ideaID`, which the browser works out, so the ID never leaves it. The server keeps that hash and the idea, and nothing else, not even when, in a table with no row numbers, so a vote says nothing of who cast it, or which other votes came from the same browser. D1's own recovery history (Time Travel) keeps each change for 30 days, with when it was made, as the privacy policy says. Clicking again takes the vote back. Triggers on `votes` keep each idea's count, a vote at a time, so a vote never counts them all again. The suggester's browser votes for its own idea as it sends it.
- **The counts are a guide.** Someone can vote twice from two browsers, and a script can cast votes with made-up hashes as fast as the limits below let it, from as many addresses as it has. A sudden jump shows on the admin page, which Steve reads anyway.
- **Limits:** suggesting and voting each go through a Workers Rate Limiting binding, 3 suggestions and 30 votes a minute from one address: an IPv4 address, or an IPv6 address's first half. Cloudflare forgets the address after the minute, and the Worker keeps none. A limit that can't be told lets the request through.
- **Where an idea stands:** new, then, once approved, to vote on (`considering`), planned, in progress, or shipped, with the release it came in, which its card links to; or not planned, which takes it off the page with its votes, ready to bring back. Merging an idea into another moves its votes there, and a browser whose vote came along sees it as its own, as the page tells it the ideas merged into each, and names that vote's hash when it votes again. A browser that voted for both counts twice. Declining a suggestion deletes it, and so does Delete in an approved idea's Change dialog, as when whoever suggested it asks, along with its votes and the ideas merged into it. After a flood of suggestions, Decline all declines every new one the page lists at once, and an address that keeps at it can be blocked in Cloudflare's dashboard. Shipped, not planned, merged and declined close an idea, which forgets its suggester's email, so the admin page offers to write to them first, as a draft in your own mail app. Each change checks the ideas again in the same batch, so two changes at once, such as two merges into each other, can't both happen.
- **The admin page,** `/roadmap/admin`, and its API under it, are for Steve alone. Cloudflare Access stands in front of them, and the Worker checks Access's signed token itself (`Cf-Access-Jwt-Assertion`): signed by the team's key, for this application's audience tag, from its team, not run out, and with an email. Until `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are set in `wrangler.jsonc`, nobody gets in. Its changes must come as JSON from the page itself, as must the roadmap's, so another site can't send one through Steve's browser. Once Access's sign-in runs out, the page says to reload it, which signs in again.

What's kept, and for how long, is in the privacy policy's Ideas and the roadmap part, and the tests check it names each column of the board's tables, so a new column waits on the policy.

## Download counts and stats
The download pages' links go to `/download/get/mac` and `/download/get/windows`. The Worker counts each download there, then sends the browser on to the newest installer on downloads.factwright.com. A count is the computer and the version, in Cloudflare's Workers Analytics Engine, which notes when, as it does for every count, and keeps each one for 3 months in the `factwright_downloads` dataset. Nothing about who downloaded is kept: no IP address, browser or ID. The privacy policy says so, so a change to what's counted needs a change to it too.

Only a person's browser following a link counts: a navigation of the whole tab, as every current browser marks one, or Chrome's Save link as. A page's script, a frame, a prefetch, a download picking up where it left off, and anything that doesn't say how it asked, such as a download tool, a browser from before 2023 or a link preview a chat service fetches on its servers, isn't counted. A preview a phone makes itself, as Apple's Messages can, may count. `robots.txt` and `rel="nofollow"` keep search engines off the links. The counts are a guide, not an exact tally: reloading a download page starts its download again, as does "Didn't start?" after a download began, and each counts, and anyone who wants to can add counts on purpose. Downloads from GitHub Releases aren't counted. Updates, which the app gets from downloads.factwright.com itself, are counted apart, below. A local preview's counts never reach Cloudflare.

Installed copies are counted where they already ask for updates, at downloads.factwright.com, by a second Worker, `factwright-updates`, so the app sends nothing for it. Its routes take only the update feeds (`latest*`) and the versioned files (`Factwright-0*` and `Factwright-Setup-0*`): the installers under fixed names keep their Cache Rule and never meet it. It hands each request on to R2 and the answer back unchanged, ranges and ETags included, counts only once the answer has gone, and if anything in it goes wrong, the request goes on as if there were no Worker. A request counts only when it carries the all-zero ID every installed copy's updater sends (`NO_INSTALL_ID` in [`apps/desktop/src/main/updates.ts`](../desktop/src/main/updates.ts)), so a browser downloading an installer, the site's Worker reading the feeds and the release workflow's checks don't. It counts two things, in the `factwright_updates` dataset, kept 3 months like the downloads:

- **A look for an update,** by computer. From 0.18.1, an open copy looks about once every 10 minutes, and when the computer wakes, so the looks in 10 minutes are about how many copies were open then, and a day's looks over 6 about the hours they were open. 0.18.0 and earlier also look each time you switch back to them, at most once a minute, so until those copies update, these run high.
- **An update picked up,** by computer and version: the newest version's block map, which a copy fetches once before downloading the parts that changed, or on a Mac without the last update to build on, its whole zip. An older version's block map, which a copy builds on, isn't counted, nor are the parts it downloads a range at a time. An update downloaded again after one that failed counts again.

Nothing about a copy is kept: no IP address, no browser and no ID. The privacy policy's Updates part says so. A real update from 0.17.0 to 0.18.0 took 79 range requests on a Mac and 12 on Windows, so each copy's update is a few dozen Worker requests, and each open copy's looks about 144 a day. On Workers Paid, as the account is, they come out of its 10 million requests a month. On the free plan, they'd share its daily 100,000 with the sync server.

The sync server keeps its own totals: once a day, its daily job counts its accounts, the ones made the day before and in the last week and month, the ones used in the last week and month, and the sign-ins that haven't ended, in the app and in browsers, and keeps only those totals, in the `factwright_sync` dataset ([`apps/server/src/sync-totals.ts`](../server/src/sync-totals.ts)).

`pnpm --filter @factwright/site stats` reads the three datasets and prints the downloads of the last 90 days, by computer and version, with the last 14 UTC days that had any; the copies open in the last full 10 minutes, and for each of the last 14 UTC days, the most open at once and the hours they were open; the copies that picked up each version in the last 90 days; and the newest sync totals, with the new accounts of the last 14 days. It reads counts only, so it can't show a name, an email or anything else about a person. The app itself reports nothing: someone who never turns on sync shows up as a download, and as their copy's looks for an update and the updates it picks up.

It needs a Cloudflare API token that can read analytics and nothing else. In the Cloudflare dashboard, under **My Profile → API Tokens → Create Token → Create Custom Token**, give it one permission, **Account · Account Analytics · Read**, for the account factwright.com runs in. It can't reach the accounts database, or change anything. Keep it in your password manager, never in a file here. The command reads it from `FACTWRIGHT_STATS_TOKEN`, not `CLOUDFLARE_API_TOKEN`, so it never stands in for Wrangler's own sign-in, and the account's ID from `CLOUDFLARE_ACCOUNT_ID`: the long code after `dash.cloudflare.com/` in the dashboard's address. To give the token to the one command, without it showing, landing in your shell's history, or staying for the commands after:

```bash
read -rs TOKEN && FACTWRIGHT_STATS_TOKEN="$TOKEN" CLOUDFLARE_ACCOUNT_ID=<the account's ID> pnpm --filter @factwright/site stats; unset TOKEN
```

With 1Password's command-line tool, `FACTWRIGHT_STATS_TOKEN="$(op read 'op://<vault>/<item>/credential')"` in place of `read` does the same.

## Deploying
It runs on Cloudflare Workers, in the same account as factwright.com. Only the pages go through the Worker: built files and template previews skip it, so a busy day on the site barely touches the daily Worker requests the account's sync server shares.

1. Sign in to that Cloudflare account, with only what a deploy needs: `pnpm --filter @factwright/site exec wrangler login --scopes account:read user:read workers:write workers_scripts:write workers_routes:write zone:read d1:write`. The deploy reads the ideas board's database, which needs `d1:write`.
2. Before the first deploy with the ideas board, once:
   - Make its database: `pnpm --filter @factwright/site exec wrangler d1 create factwright-feedback`. The deploy finds it by name. Without it, the deploy would make one on its own, with no tables yet.
   - Make an Access application in the account's Zero Trust dashboard, under **Access → Applications → Add an application → Self-hosted**, for `factwright.com/roadmap/admin`, which covers what's under it, with a policy that lets in only Steve's email. Then put its team's domain, such as `factwright.cloudflareaccess.com`, in `ACCESS_TEAM_DOMAIN`, and its **Application Audience (AUD) Tag** in `ACCESS_AUD`, both in `wrangler.jsonc`.
3. Make the ideas board's tables, or bring them up to date: `pnpm --filter @factwright/site exec wrangler d1 migrations apply factwright-feedback --remote`. Run it again after a change to `migrations`, before deploying it.
4. `pnpm --filter @factwright/site run deploy` builds the site and deploys the `factwright-site` Worker. It needs `run`, as `pnpm deploy` on its own is a different pnpm command. Its first deploy set up factwright.com and www.factwright.com on their own.
5. `pnpm --filter @factwright/site run deploy:updates` deploys the `factwright-updates` Worker in front of downloads.factwright.com's update files, with its routes. Deploy it on its own: the site's deploy doesn't touch it. Afterwards, check that the feeds and an update file's ranges answer as before, with `curl -sI`.
6. `pnpm --filter @factwright/site exec wrangler logout`.
